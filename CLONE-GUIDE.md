# Activity Clone Guide — "Initiate Submission Request" as the Golden Template

**Purpose:** Produce 10–15 clones of an activity that are **100% identical in structure** to
*Initiate Submission Request*, with zero rework.

**Reference activity (the template):**
- Activity Definition: `sys_pd_activity_definition` · `45c5037568a5483aa51faf7ed0171f45`
- Label: `Initiate Submission Request`
- Internal name: `x_gegis_ins_policy_initiate_submission_request`

> ⚠️ **Read "Section 6 — Hard Rules / Gotchas" before you build anything.** Most failures in this
> app came from ignoring those points.

---

## 0. Golden decisions (locked — do not deviate)

| Decision | Value | Why |
|---|---|---|
| **Target table** for every clone | `global` | Per owner instruction. Do **not** use `x_gegis_ins_policy_submission` (that was template-specific). |
| **Where you build** | On the **instance** (Studio / Playbook Designer / UI Builder) | The working UI screen graph **cannot** be hand-authored as XML. |
| **Fluent source** (`src/fluent/playbook/clearance-playbook.now.ts`) | **Do NOT edit** | It is **stale** (e.g. it still has old `source=db1084e5…`; the instance uses `cb18ceef…`). Only touch if explicitly needed. |
| **Sync path** | Build on instance → **Commit** → it flows to the repo (`43b656…/update`) | Repo→instance pulls have been unreliable for these hand-authored records. |

## 5. Step-by-step build procedure (instance — the safe path)

Do this **per clone**:

1. **Activity Definition** — Studio → Policy Suite → Activity Definitions → **New**.
   - Set `Label`, internal `Name` (`x_gegis_ins_policy_<new>`), `Table = global`.
   - Backing flow (`source`) = the shared **Base Playbook Activity Flow** (`cb18ceef…`), `source_type = sys_hub_flow`.
   - `Category = Interactive`, `Access = public`, `Wait for completion = true`.
2. **UI Layout + 6 properties** — created with the activity type. Confirm color `#F1F6DB`, Pink-1 category, icon `news_outline`. Verify the 6 experience properties exist (Section 4, Layer 3).
3. **Activity UI screen (UI Builder)** —
   - Open Initiate Submission Request's **real** variant in the Playbook Experience Builder → click **Duplicate**.
   - **Rename** the duplicate to `<New Label> UI`.
   - Set its `experience_type` to the new UI Layout and `playbook_experience = Global`.
   - On the new **UI Layout** (`sys_pd_activity_type`), set **Default Activity UI** = this new variant.
4. **Playbook Actions** — open the new Activity Definition → **Playbook Actions** related list →
   add the **3** declarative actions (Restart Activity / Skip / Mark Complete), Playbook Experience = Global.
   *(Clear the search box if the list looks empty — see Gotchas.)*
5. **Process placement** — in Process/Playbook Designer, drag the new activity onto the clearance
   process diagram where it belongs.
6. **Commit** via Source Control → the records flow to `43b656…/update` in the repo.
7. **Run the verification checklist (Section 7).**

## 6. Hard rules / gotchas (the lessons that cost us time)

1. **UI Builder screens are NOT hand-authorable.** Writing `sys_ux_screen` / `sys_ux_macroponent`
   XML by hand produces *"Activity UI is missing a corresponding screen in UI Builder."* Always
   **Duplicate** an existing **real** screen in UI Builder. (The template's real variant is
   `02352bb2…befdc37`.)
2. **Two variants exist per activity — use the REAL one.** Synthetic variants (`c2ea…`, `b25b…`,
   and `…eb0` "Activity UI" records, plus `sys_ux_screen …ead`) are hand-authored skeletons and are
   **broken in UI Builder**. Do not copy them.
3. **Never reuse the template's sys_ids** and never invent sequential ones (`c4ea0001…`). Those
   synthetic sequential ids are exactly what made source-control sync unreliable. Let the instance
   generate real random sys_ids.
4. **`default_activity_ui` is reference-qualified** to variants whose `experience_type` = that exact
   layout, that are **Active**, under the **same playbook experience**. If your new variant won't
   attach, that's the reason — fix `experience_type` / `Active` / Global experience.
5. **The "Base Activity UI Layout" has no real variant** — don't use it as a screen template.
6. **Empty Playbook Actions list?** Clear the related-list **search box** (a leftover `zztextsearch`
   filter hides everything) before concluding records are missing.
7. **Build on the instance, not in Fluent.** `clearance-playbook.now.ts` is stale and will diverge.
8. **A pull that says "no files were updated"** means the instance already matches the committed
   repo — it is **not** applying your synthetic records. Verify on the form, not by the pull dialog.
